# Эксперимент: Go-подобный рантайм на greenlet поверх free-threaded Python

Дата: 2026-10-09. Машина: Apple M2 Pro, 10 ядер (6 P + 4 E), macOS. Python 3.14.6 и 3.14.6t (uv),
greenlet 3.5.6. Каждая конфигурация прогнана один раз, цифры ориентировочные (разброс ~5–10 %).

Код: `gort.py` (рантайм: hub на поток, kqueue-селектор, кооперативные сокеты, `go`, `Chan`,
`spawn_blocking`), `bench.py` (драйвер), `echo_server.py` («база»: 4 asyncio-процесса на GIL-сборке),
`run_matrix.sh` (матрица), `baseline.py` / `baseline_proc.py` (потолок масштабирования без рантайма).

Запуск: `./run_matrix.sh` (нужны `.venv-ft` и `.venv-gil`, см. ниже).

```
uv venv -p 3.14t .venv-ft && uv pip install -p .venv-ft/bin/python greenlet
uv venv -p 3.14  .venv-gil && uv pip install -p .venv-gil/bin/python greenlet
```

## Вопросы, на которые отвечал эксперимент

1. Работает ли greenlet на 3.14t и не включает ли он GIL обратно?
2. Масштабируется ли модель «N hub'ов в N потоках» по ядрам на free-threaded сборке?
3. Что она даёт против простого пула OS-потоков с блокирующими сокетами?

## Выводы

1. **greenlet 3.5.6 на 3.14t работает.** `sys._is_gil_enabled()` остаётся False после импорта, ни одного
   крэша за всю матрицу (известный issue про редкие падения не воспроизвёлся).
2. **Модель масштабируется только на free-threaded сборке.** На GIL-сборке добавление hub'ов делает хуже
   (I/O: 32k → 16k при 8 hub'ах из-за борьбы за GIL). На ft: CPU ×3.2, mixed ×2.9, I/O ×2.0 при 8 hub'ах.
3. **Потолок задаёт не рантайм, а машина и интерпретатор.** Голые ft-потоки на этой машине дают те же
   ~2.8–3× на 8 потоках, что и hub'ы, процессы дают ~4.3×. Разница потоки/процессы это цена free-threaded
   (refcount, аллокатор) плюс E-ядра M2. Thread-local bytecode (TLBC, включён по умолчанию) критичен:
   без него масштабирование исчезает полностью.
4. **Против OS-потоков выигрыш не в rps, а в памяти.** На ft пул из 200–1000 блокирующих потоков даёт ту же
   или чуть большую пропускную способность, но стоит +120–240 MB RSS против +12–31 MB у hub'ов. На чистом
   I/O потоки даже быстрее (80k против 65k): прототипный hub регистрирует и снимает fd в kqueue на каждое
   ожидание, это оптимизируемо.
5. **Кооперативность работает:** 1000 одновременных соединений с 1 мс ожиданием на 8 hub'ах обслуживаются
   быстрее, чем 1000 OS-потоков, при ~8× меньшей памяти.

## Что не проверялось

- Стабильность greenlet на 3.14t под длительной нагрузкой и при остановке (issue про крэши).
- Linux/epoll: все числа с macOS/kqueue.
- Драйверы с C-ядром (psycopg, grpcio) в кооперативном режиме; здесь только чистые сокеты.
- Справедливость и хвосты латентности: замерялась только пропускная способность.
