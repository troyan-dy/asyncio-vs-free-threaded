# Эксперимент 2: синхронный HTTP-сервис с фоновыми обновлениями стейта на free-threaded Python

Дата: 2026-10-09. Та же машина (M2 Pro, 10 ядер), Python 3.14.6 / 3.14.6t, greenlet 3.5.6,
Flask 3.1.3, waitress. Каждая конфигурация прогнана один раз, 64 keep-alive соединения, 10 секунд.

## Что проверялось

Сервис в духе Flask, весь код синхронный. Фоном крутятся три задачи, которые меняют общий стейт:

- перечитывание `config.json` по mtime (файл переписывается бэкендом каждые 2 с),
- разбор push-стрима (аналог gRPC-стрима: 64-байтные сообщения каждые 10 мс) в снапшот котировок,
- ротация всех соединений к «базе» каждые 3 с без остановки обработки запросов.

Хендлер `/quote`: один поход в «базу» (echo с задержкой 1 мс через пул соединений) плюс 20 000 итераций
чистого Python (~0.6 мс CPU), в ответе версия конфига, seq стрима и поколение пула. Нагрузочный генератор
проверяет, что все три числа растут во время прогона.

Три реализации одного и того же приложения (`demo_app.py` общий):

- `greenlet N`: мини-фреймворк `miniflask.py` поверх `gort.py`, N hub-потоков, кооперативные сокеты;
- `threads`: тот же мини-фреймворк поверх `rt_threads.py`, OS-поток на соединение, блокирующие сокеты;
- `flask`: настоящий Flask под waitress (пул из 64 потоков, keep-alive), фоновые задачи как daemon-потоки.

Запуск: `./run_http_matrix.sh` (бэкенды поднимаются сами). Смотреть код: `demo_app.py`, `miniflask.py`.

## Как это выглядит в коде

```python
app = App(rt)
state = State()                      # держатель иммутабельных снапшотов

@app.startup
def connect_db():                    # пулы создаются один раз, общие для всех потоков/hub'ов
    pools.append(Pool(rt, addr, size=8))

@app.every(1.0)                      # периодическая фоновая задача
def reload_config():
    if mtime changed:
        state.config = Config(...)   # публикация = присваивание нового объекта

@app.every(3.0)
def rotate_db_connections():
    for p in pools: p.rotate()       # пересоздание коннектов под живой нагрузкой

@app.daemon                          # долгоживущий цикл, при падении перезапускается
def consume_stream():
    s = rt.socket(); s.connect(STREAM_ADDR)
    while True:
        seq, sym, value = parse(s.recv_exactly(64))
        state.rates = {**state.rates, sym: value}   # новый dict, старый не мутируем
        state.stream_seq = seq

@app.get("/quote")
def quote(req):
    cfg, rates = state.config, state.rates          # консистентный снапшот на запрос
    with pool.acquire() as conn:                    # I/O
        conn.send_all(QUERY); conn.recv_exactly(64)
    checksum = cpu_work(cfg.cpu_iters)              # CPU
    return json.dumps({...}).encode()
```

Хендлеры и фоновые задачи это обычные `def`. Какой исполнитель под ними, greenlet на hub'е или OS-поток,
решает рантайм, код приложения не меняется. Никаких `await`, `go`, каналов в пользовательском коде нет.

## Результаты (64 соединения, 10 с)

| gil greenlet 1 hub | 1 450 | 43.5 | 68 | 77 | 298 | 17 MB | да |
| gil greenlet 4 hubs | 1 359 | 29.9 | 138 | 245 | 652 | 17 MB | да |
| gil greenlet 8 hubs | 1 407 | 31.5 | 142 | 246 | 609 | 20 MB | да |
| gil threads | 1 442 | 37.8 | 92 | 137 | 886 | 21 MB | да |
| gil flask + waitress | 1 175 | 46.7 | 96 | 144 | 1167 | 35 MB | да |
| ft greenlet 1 hub | 1 444 | 41.3 | 67 | 153 | 382 | 20 MB | да |
| ft greenlet 4 hubs | 3 670 | 13.6 | 41 | 72 | 297 | 25 MB | да |
| ft greenlet 8 hubs | 4 520 | 11.7 | 31 | 50 | 243 | 27 MB | да |

«Стейт обновлялся»: за прогон версия конфига выросла на 5–6, seq стрима на ~900 (10 мс такт),
поколение пула с 1 до 4 (ротация каждые 3 с). Ошибок 0 во всех конфигурациях.

## Выводы

1. **Фоновые задачи не голодают ни в одном рантайме.** Под полной нагрузкой конфиг, стрим и ротация
   пула шли по расписанию. Для greenlet это не было очевидно: там нет вытеснения, но хендлер паркуется
   на каждом I/O, и фоновые greenlet'ы получают своё время.
2. **Настоящий Flask без изменений кода ускорился в 4 раза**, 1.2k → 4.9k rps, просто от смены сборки
   на 3.14t и waitress с 64 потоками. Это главный практический результат: для синхронного стека
   free-threaded работает «из коробки», без нового рантайма.
3. **OS-поток на соединение даёт максимум rps** (6.6k) и лучший p50 (3.4 мс), но худшие хвосты
   (p99 95 мс против 50 у greenlet 8) и ×3 памяти. 64 runnable-потока на 10 ядрах вытесняют друг друга
   посреди CPU-куска, кооперативные hub'ы дорабатывают запрос до конца.
4. **greenlet-hub'ы это компромисс:** меньше rps, чем у потоков (4.5k), но ровнее хвосты и 27 MB RSS.
   Выигрыш по памяти станет решающим на тысячах соединений, при 64 он не критичен.
5. **На GIL-сборке больше одного hub'а вредно:** rps не растёт, а p99 ухудшается втрое (77 → 245 мс)
   из-за борьбы hub'ов за GIL. Многопоточный рантайм включать только при `sys._is_gil_enabled() == False`.
6. **Общий пул соединений между потоками в sync-модели работает.** В asyncio соединение привязано к
   loop'у через его Future'ы, здесь ожидание это «зарегистрируй fd в селекторе текущего hub'а», поэтому
   пул создаётся один раз и используется с любого hub'а. Первая версия прототипа привязывала сокет к
   hub'у при создании и падала с «Cannot switch to a different thread» ровно по этой причине.

## Что не проверялось

- Linux/epoll, длительная стабильность greenlet на 3.14t, остановка сервера.
- Настоящие драйверы (psycopg, grpcio): здесь «база» и «стрим» на чистых сокетах.
- Тысячи соединений: при 64 преимущество greenlet по памяти видно слабо.
- Werkzeug dev server отвечает `Connection: close` на каждый запрос, поэтому для Flask взят waitress;
  с werkzeug на ft нагрузка выжигала эфемерные порты macOS за 10 с.
